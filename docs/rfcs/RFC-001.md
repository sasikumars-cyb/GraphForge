# RFC-001: Engineering Session

**Status:** Implemented
**Architecture baseline:** GraphForge Architecture v2.1 (approved and frozen)
**Scope:** The Engineering Session aggregate — `EngineeringSession`, `Timeline`,
`WorkingUnderstanding`, `Participant`, `Belief`, `Hypothesis`, `Evidence`,
`Recommendation`, `Decision`, `Contradiction`.

This RFC is the first production implementation built on Architecture v2.1.
It does not introduce, simplify, or reinterpret any architectural concept —
where implementation raised a question the architecture didn't answer, that
question is recorded below as a documented scope boundary, not resolved by
invention.

> **Known open conflict with the normative Engineering State contract.**
> [`docs/graphforge/ENGINEERING_STATE_ARCHITECTURE.md`](../graphforge/ENGINEERING_STATE_ARCHITECTURE.md)
> (canonical, normative for Engineering State) later defined `Belief`,
> `Hypothesis`, `Evidence`, and `Decision` with different, incompatible
> semantics from this RFC's — notably, that contract requires Belief
> confidence to be derived from an append-only Evidence trail, never
> manually mutated, where this RFC's own §3.2 states "a Belief is 'mutated
> in place, never versioned.'" This is an explicitly flagged, unresolved
> collision (see the contract's §0), not something to silently reinterpret
> in either direction. This RFC's description below remains an accurate
> record of what `EngineeringSession` actually implements; it is not
> automatically conformant with the later contract, and reconciling the two
> requires its own explicit architectural decision.

---

## 1. Summary

Engineering Session is the aggregate root Architecture v2.1 §2.2 describes as
the unit of "an engineer's continuous line of reasoning about a piece of
work." This RFC implements it end-to-end: relational persistence (joined-table
inheritance for the `EngineeringArtifact` supertype), eight services carrying
the domain's business rules, a 20-endpoint REST API, and a full test suite
(schema, repository, service, and HTTP-level) covering every invariant the
architecture specifies for this aggregate.

## 3. Domain model

### 3.1 Aggregate boundary

`EngineeringSession` is the aggregate root. It owns, by composition (cascade
delete), its `TimelineEntry` rows and every `EngineeringArtifact` row created
within it. No Engineering Artifact exists independent of a Session, and no
service or endpoint in this RFC can act on an artifact through a URL naming
a different Session than the one it actually belongs to — `_require_same_session`
in the router enforces this at the API boundary as a 404, and every repository
query used for cross-artifact lookups (e.g. `ContradictionRepository.list_by_artifact`)
is itself Session-scoped by its caller.

### 3.2 `EngineeringArtifact` inheritance

Modeled as joined-table inheritance: `engineering_artifacts` carries the five
fields Architecture v2.1 §6 requires "defined exactly once at the supertype" —
id, session ownership, authoring Participant, retention state, creation time —
and each concrete subtype (`beliefs`, `hypotheses`, `evidence`, `decisions`,
`recommendations`, `contradictions`) shares that same primary key as its own
PK+FK. This is what lets `Contradiction` reference "two or more disputing
Engineering Artifacts" (§2.2, Δ v2.1) through one real foreign key
(`contradiction_parties.artifact_id → engineering_artifacts.id`) regardless of
which concrete type each disputing party actually is.

### 3.3 Contradiction ownership

`Contradiction.owner_scope` encodes "always the narrowest scope containing
every disputing party." In this RFC that is only ever `"session"` — Mission
and Organization don't exist as tables yet (§5.4), so those wider scopes in
the ownership rule are not reachable code paths. The column is scoped by a
`CHECK` constraint to its one currently-valid value; widening it later
(Mission-scoped Contradictions) is an additive migration, not a rename.

### 3.4 Belief lifecycle

A Belief is "mutated in place, never versioned" (§2.2) — `BeliefService.revise_belief`
updates the same row's `statement`/`confidence` rather than creating a new
version. A Hypothesis is the only versioned/sequential object here: it
resolves into exactly one Belief (`resolved_belief_id`) or is rejected; it is
never itself revised in place.

## 4. Services

Eight services, each with one clear responsibility, matching the architecture's
own service boundary (no cross-cutting "god service"):

- **SessionService** — create, fetch, list (paginated), status transitions.
- **TimelineService** — append (assigns the next monotonic per-session
  sequence number under the caller's transaction), paginated read.
- **UnderstandingService** — assembles `WorkingUnderstanding` live from
  Belief rows; computes `overall_confidence` as an average. No persistence.
- **BeliefService** — Belief and Hypothesis together (a Hypothesis's only
  reason to exist is resolving into a Belief, so they're never reasoned
  about separately): propose, update confidence, resolve, reject, revise,
  retract.
- **EvidenceService** — record (append-only; no update/delete method exists
  at any layer), paginated read.
- **RecommendationService** — propose (with automatic competing-Recommendation
  → Contradiction detection), accept, decline.
- **ContradictionService** — detect (enforces a minimum of two parties and
  that every party belongs to the same Session), resolve, mark unresolved.
- **DecisionService** — commit (enforces the propose/commit boundary),
  supersede (creates a new row, points the old one's
  `superseded_by_decision_id` at it — never edits the original).

`app/services/participant_helpers.py` (`get_or_create_human_participant`,
`get_or_create_agent_participant`) is deliberately **not** a ninth service —
Architecture v2.1 names no Participant service, and this module has no
business rules of its own; it only resolves the current human/agent-role
into a `Participant` row for the eight real services to attribute artifacts to.

Every service owns its own transaction boundary and narrates every mutation
onto the Timeline via `TimelineService.append` — no mutation in this RFC is
silent.

## 5. Known limitations (documented scope boundaries, not deviations)

- **No promotion (copy-with-provenance).** Architecture v2.1 §2.2 (Δ v2.1)
  specifies that a Belief is never itself promoted — only an independent
  `SystemModelEntry` is, via copy-with-provenance, and that object belongs to
  the System Model aggregate (Phase 3), out of this RFC's scope. `Belief` has
  no `promoted_at`/`promoted_to` field, and no service exposes a `promote_belief`
  method. This RFC implements everything up to and including Belief formation,
  revision, and retraction — promotion is the next RFC's work, not a gap in
  this one.
- **No Mission or Organization.** `EngineeringSession.mission_id` is a plain,
  nullable, unconstrained UUID column — reserved for the Mission aggregate a
  later RFC introduces. Adding the FK then is additive. `Contradiction.owner_scope`
  is likewise constrained to only `"session"` today for the same reason.
- **No Policy.** Architecture v2.1's resolution of review finding 1 makes
  retention/legal-hold a field on Engineering Artifact directly (implemented:
  `retention_state`), not a Policy instantiation — Policy itself (§5.4,
  Phase 7) is out of scope for this RFC. The propose/commit boundary
  (§5's "only humans commit") is enforced directly in `DecisionService`, not
  expressed as a Policy rule, for the same reason.
- **`list_sessions` is intentionally unscoped.** With no Organization/Mission
  table yet, there is no natural filter to scope a session list by — it
  returns every Session in the database, paginated. A later RFC introducing
  Mission will add that scope as an additional, additive query parameter.
- **Migration verified manually, not via automated upgrade/downgrade test in
  CI.** The migration (`42c15cf49ec2`) was run upgrade → downgrade → re-upgrade
  against a real Postgres instance and confirmed to leave unrelated tables
  untouched (see Migration Guide). `test_engineering_session_schema.py`
  asserts the *ORM model shape* the migration was generated from and hand-
  verified to match, rather than re-running the migration itself inside the
  test suite — a deliberate choice to avoid a destructive schema operation
  inside the shared test database's transactional-rollback fixture, not an
  oversight.
- **`Recommendation.target_contradiction_id` has no foreign key.** See
  `app/models/decision.py`'s module docstring — enforcing it would create a
  genuine circular table dependency (`recommendations → contradictions →
  decisions → recommendations`). The field is documented, unenforced, and
  read-only for display purposes, the same pattern already used for
  `EngineeringSession.mission_id` and `TimelineEntry.artifact_id`.
- **Duplicate-work / cross-session detection is out of scope.** Nothing in
  this RFC compares a new Hypothesis or Recommendation against ones in other
  Sessions — Architecture v2.1 doesn't ask for this at the Engineering
  Session aggregate level (it is a Knowledge Architecture concern, §7,
  separately scoped).

## 6. Migration guide

Migration: `alembic/versions/42c15cf49ec2_add_engineering_session_aggregate_rfc_.py`

**New tables (creation order matters — matches FK dependency order):**
`participants` → `engineering_sessions` → `engineering_artifacts` →
`timeline_entries`, `beliefs`, `evidence`, `hypotheses`, `recommendations` →
`decisions` → `contradictions`, `contradiction_parties`.

**Cascade rules:**
- `engineering_sessions` deleted → cascades to its `timeline_entries` and
  `engineering_artifacts` (and, transitively, every concrete artifact table,
  each of which cascades from `engineering_artifacts.id`).
- `contradictions` deleted → cascades to its `contradiction_parties` rows.
- `participants` deleted → `RESTRICT`s on every artifact/timeline FK that
  names an author (a Participant with authored history cannot be deleted);
  `SET NULL` on `engineering_sessions.created_by_participant_id` (a Session
  survives its creator's Participant row being removed).

**Constraints:**
- `ck_participants_kind_shape` — a Participant is exactly one of
  (`kind='human'`, `user_id` set, `agent_role` NULL) or
  (`kind='agent'`, `agent_role` set, `user_id` NULL).
- `ck_engineering_artifacts_retention_state` — `active | legal_hold | redacted`.
- `ck_contradictions_owner_scope` — currently only `session` (see §5).
- `uq_timeline_entries_session_sequence` — one turn per (session, sequence).
- `uq_contradiction_parties_pair` — a given artifact can be a party to a
  given Contradiction at most once.

**Running it:**
```bash
cd backend
DATABASE_URL="postgresql+asyncpg://graphforge:graphforge@localhost:5433/graphforge" \
  .venv/bin/alembic upgrade head
```
(Adjust the port to match your `docker-compose` Postgres mapping — this
repo's dev compose maps the container's 5432 to host 5433, not 5432, which
differs from the default in `.env`.)

**Rollback:** `alembic downgrade -1` — verified to cleanly reverse all of the
above with no orphaned tables or constraints, and confirmed not to touch any
pre-existing table (`knowledge_connections`, `llm_invocations`) outside this
RFC's scope.

`alembic/env.py` now imports all seven new model modules so Alembic
autogenerate's `target_metadata` can see them — a model added to
`app/models/` without a corresponding import there is invisible to future
autogenerate runs, independent of this RFC.

## 7. API

All endpoints are under `/api/v1/sessions`, require authentication
(`Depends(get_current_user)`), and use the DTOs in
`app/schemas/engineering_session.py` for request validation and response
serialization. Paginated list endpoints return a `Page` envelope
(`{items, page: {total, limit, offset}}`).

| Method | Path | Purpose |
|---|---|---|
| POST | `/sessions` | Create a Session |
| GET | `/sessions` | List Sessions (paginated, optional status filter) |
| GET | `/sessions/{id}` | Fetch a Session |
| PATCH | `/sessions/{id}/status` | Transition Session status |
| GET | `/sessions/{id}/timeline` | Paginated Timeline read |
| GET | `/sessions/{id}/understanding` | Working Understanding (live-assembled) |
| POST | `/sessions/{id}/hypotheses` | Propose a Hypothesis |
| GET | `/sessions/{id}/hypotheses` | List Hypotheses |
| POST | `/sessions/{id}/hypotheses/{hid}/resolve` | Resolve into a Belief |
| POST | `/sessions/{id}/hypotheses/{hid}/reject` | Reject a Hypothesis |
| GET | `/sessions/{id}/beliefs` | List Beliefs |
| POST | `/sessions/{id}/beliefs/{bid}/revise` | Revise a Belief in place |
| POST | `/sessions/{id}/beliefs/{bid}/retract` | Retract a Belief |
| POST | `/sessions/{id}/evidence` | Record Evidence |
| GET | `/sessions/{id}/evidence` | Paginated Evidence read |
| POST | `/sessions/{id}/recommendations` | Propose a Recommendation |
| GET | `/sessions/{id}/recommendations` | List open Recommendations |
| POST | `/sessions/{id}/recommendations/{rid}/accept` | Accept |
| POST | `/sessions/{id}/recommendations/{rid}/decline` | Decline |
| POST | `/sessions/{id}/decisions` | Commit a Decision (human only) |
| GET | `/sessions/{id}/decisions` | Paginated Decision read |
| POST | `/sessions/{id}/decisions/{did}/supersede` | Supersede with a new Decision |
| POST | `/sessions/{id}/contradictions` | Detect a Contradiction (≥2 parties) |
| GET | `/sessions/{id}/contradictions` | Paginated Contradiction read |
| POST | `/sessions/{id}/contradictions/{cid}/resolve` | Resolve |
| POST | `/sessions/{id}/contradictions/{cid}/mark-unresolved` | Mark unresolved |

Every mutating request except `POST /decisions` accepts an optional
`agent_role` field: present, it records the artifact as authored by that
Agent Participant; absent, the calling authenticated human is the author.
`POST /decisions` has no such field — the propose/commit boundary means a
Decision's committer is always the calling human, at the schema level as
well as the service level.

## 9. Architecture compliance audit

| Class / Concept | Verdict | Notes |
|---|---|---|
| `EngineeringSession` | Conforms | Aggregate root; owns Timeline + Artifacts by composition/cascade exactly as §2.2 specifies. |
| `TimelineEntry` (Timeline) | Conforms | Append-only — no update/delete code path exists at any layer; monotonic per-session sequence. |
| `WorkingUnderstanding` | Conforms | Non-persisted, always live-assembled from Beliefs, matching §2.2's "composed of Beliefs" literally rather than as a cached/derived table. |
| `Participant` | Conforms | Unified Human/Agent supertype; fixed, closed Agent roster (§5) enforced against `AGENT_ROLES`, not free text. |
| `EngineeringArtifact` | Conforms | Real relational supertype via joined-table inheritance; every subtype shares one identity/traceability contract (§6). |
| `Belief` | Conforms | Mutated in place, never versioned; no promotion method exists (promotion is explicitly out of scope, §5). |
| `Hypothesis` | Conforms | Resolves into exactly one Belief via a real FK, or is rejected — the only versioned/sequential object in this aggregate. |
| `Evidence` | Conforms | One uniform model across all four named subtypes (§2.2); append-only. |
| `Recommendation` | Conforms | Competing Recommendations resolved via Contradiction — no separate conflict mechanism was invented. |
| `Decision` | Conforms | Propose/commit boundary enforced independently at both the service and API/schema layers; supersession is additive (new row), never an edit. |
| `Contradiction` | Partially conforms | N-ary and mixed-type as specified (Δ v2.1); ownership-scope rule is implemented but only its `"session"` branch is reachable — the Mission/Organization branches require aggregates this RFC doesn't build (documented in §5, not a deviation from the rule itself). |
| Policy references | Does not apply / out of scope | Architecture v2.1's own resolution of review finding 1 moved retention/legal-hold onto Engineering Artifact directly; Policy itself (§5.4) is Phase 7, not part of this RFC's objectives. |
| Mission / Organization | Does not apply / out of scope | Not part of RFC-001's objectives; `mission_id` reserved as an additive, unconstrained column for the RFC that introduces Mission. |
| copy-with-provenance promotion | Does not apply / out of scope | Belongs to the System Model aggregate (Phase 3), not the Engineering Session aggregate this RFC implements. |

**Overall verdict:** every class this RFC was scoped to build conforms to
Architecture v2.1. The two "does not apply" rows are not gaps in this
RFC's own objectives — they name concepts Architecture v2.1 places in later
phases and other aggregates, listed here for traceability rather than left
silent.

## 10. Implementation notes

- Postgres in this dev environment is host-mapped to `5433`, not the `5432`
  in `.env`'s `DATABASE_URL` default — manual migration/test runs in this RFC
  used an overriding `DATABASE_URL` environment variable; `.env` itself was
  not changed.
- `ContradictionParty`'s two relationships (`Contradiction.parties` and
  `ContradictionParty.contradiction`) both declare explicit `foreign_keys=`
  — without it, SQLAlchemy sees an ambiguous second join path back to
  `engineering_artifacts` (since `Contradiction` is itself an
  `EngineeringArtifact` subtype, and could in principle be a party to a
  *different* Contradiction).
- `SessionService.list_sessions`'s own test asserts a relative increase
  (`baseline_total + N`) and ID-subset containment rather than an absolute
  row count — the method is deliberately unscoped (§5), so an absolute-count
  assertion would be fragile against any pre-existing data in a shared
  database.
