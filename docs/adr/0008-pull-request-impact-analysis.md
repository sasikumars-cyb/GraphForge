# ADR 0008: Deterministic pull request impact analysis

## Status
Accepted

## Context
The ask: given a pull request, determine every component that could be affected using the Knowledge Graph Phase 6's indexer built — changed services, downstream services, REST APIs, Kafka topics, shared libraries, and the dependency chains that explain why each is impacted. No AI/LLM involvement, everything deterministic, following the workflow: read changed files → map to indexed graph nodes → traverse Neo4j relationships → return risk + impact.

The available inputs are narrow and matter a lot for what's actually achievable deterministically: a pull request's changed *file paths* (not diff content, not an AST-level before/after comparison), and the *single, currently-indexed* graph for that repository (there is no stored "graph as of the PR's base commit" to diff against — indexing always fully replaces the prior graph, per ADR 0007). Every decision below follows from working within those two constraints honestly, rather than pretending to a precision the inputs don't support.

## Decisions

**File-path mapping, not diff-content analysis.** A changed file's path is matched directly against the `file_path` property already stored on Controller/Endpoint/Service/FeignClient/Component nodes (set by the indexer using the same repo-root-relative convention GitHub's PR files API uses) — no AST diffing, no line-level analysis. This is coarse-grained by design: touching *any* line of a file marks its *whole* owning component as directly impacted, not just the specific method that changed. That's the correct, conservative choice for a system that must never guess — see ADR 0007's parsing philosophy for the same principle applied to extraction.

**Risk classification — Controller changes are MEDIUM, not LOW.** The originally-stated rules ("LOW: controller or internal implementation changes" vs "MEDIUM: REST API or service contract changes") conflict once you notice a Controller node *is* the REST API in this graph's vocabulary — there's no separate signal available to distinguish "changed the controller's internal logic" from "changed its REST contract" without a before/after endpoint diff, which isn't available (see Context). This was raised explicitly and confirmed with the user: a Controller or Service change is **MEDIUM** (it touches the REST API / service contract surface); **LOW** is reserved for changes that don't map to any discovered architecture node at all (DTOs, config, tests, anything outside what the indexer tracks). The full, current rule set (highest-precedence trigger wins), in `app.analysis.services.risk_classifier`:
- **HIGH** — a changed file is `pom.xml` (shared library/dependency change); OR a directly-changed node produces to or consumes from a Kafka topic (schema changes have no compiler-enforced contract, so any touch is conservatively treated as a possible schema change); OR a directly-changed node is a `FeignClient` (this service's own declared calling contract against an external API — a "breaking public API change" candidate).
- **MEDIUM** — a directly-changed node is a `Controller` or `Service`.
- **LOW** — none of the above.

**Cross-repository "downstream services" via Kafka topic-name matching, not graph edges.** No edge in this graph ever crosses a `repository_id` boundary (each repository is indexed and namespaced independently — ADR 0007). But two different repositories' `KafkaTopic` nodes can share the same `name` property, and that *is* a real coupling: if repo A produces to `order-created` and repo B (indexed separately) consumes from a topic also named `order-created`, a change to A's producer genuinely can break B. `Neo4jImpactGraphReader.find_cross_repository_topic_peers` finds this by matching topic *names* across repositories rather than traversing an edge — the one place in this codebase a "relationship" is inferred from data equality instead of a stored graph edge, and it's called out explicitly here because it's a deliberate exception to "traverse relationships," not an oversight. This is the single feature that makes "downstream services" mean anything across service boundaries, which is the whole point of a change-impact tool for microservices — worth the exception.

**No cross-repository REST/Feign correlation.** A `FeignClient` node records its target's declared *name* and *URL* (e.g. `payment-service`, `http://payment-service:8080`), but nothing in the graph maps that string back to a specific indexed repository's Controller — there's no "service identity" concept shared between how a Feign client names what it calls and how a Controller identifies what it exposes. Attempting to guess a match (e.g. fuzzy-matching `target_name` against repository names) would violate "everything must be deterministic" by introducing exactly the kind of unreliable inference this project explicitly avoids. `impacted_apis` for a changed FeignClient is limited to its own declared remote-call descriptions; correlating that to another repository's actual Controller is a documented gap, not a built feature.

**One `IImpactGraphReader`, separate from `IGraphRepository`.** `app.graph.IGraphRepository` (Phase 6) is a generic graph read/write port — get the full graph, get nodes by label, replace a repository's graph. Impact analysis needs specific, purpose-built traversals (map files to nodes; walk `EXPOSES`/`CALLS` to endpoints; walk `PRODUCES_TO`/`CONSUMES_FROM` to topics and their peers; list a repository's dependencies) that don't belong on a generic graph-storage contract. `app.analysis.graph.Neo4jImpactGraphReader` is the one real implementation, reading from the same Neo4j database `IGraphRepository` writes to.

**Synchronous, not a background job.** Unlike indexing (a slow clone-and-parse pipeline that justified `BackgroundTasks` — ADR 0007), analysis is just a handful of Neo4j queries plus one GitHub API call for the changed-file list. `POST /pull-requests/{id}/analyze` runs the whole pipeline in the request/response cycle and returns the result directly — no job-status polling needed for something this fast.

**One persisted analysis per pull request, replaced on re-run.** `PullRequestAnalysis.pull_request_id` is unique; re-analyzing overwrites rather than accumulating history — the same "always replace, never diff against the prior run" philosophy Phase 6's indexing uses for its graph. `GET /pull-requests/{id}/analysis` reads whatever was last computed; `POST .../analyze` always computes fresh.

**`list_changed_files` fetches a single page (up to 100 files).** Matches this codebase's existing `list_repositories` precedent of not exhaustively paginating GitHub list endpoints (see ADR 0006). A pull request touching more than 100 files will only have its first 100 analyzed — a known, documented limitation, not silent truncation.

## Scope boundaries (explicitly not built)
- Diff-content or AST-level change analysis — only file-path-level mapping (see Decisions above for why).
- A before/after graph diff to detect actual endpoint additions/removals/signature changes — would require re-indexing both `base_ref` and `head_ref` and comparing two `ArchitectureModel`s; not needed for the stated workflow (map files → traverse), and a natural next step if precision beyond "which files touched which components" is ever required.
- Cross-repository REST/Feign correlation (see Decisions above).
- Pagination beyond 100 changed files per pull request.
- Any AI/LLM involvement anywhere in this pipeline — every step is a deterministic lookup, string match, or graph traversal.

## Verification strategy
- `tests/unit/analysis/` — `classify_risk`, `build_dependency_paths`, and the node-display helpers (`primary_label`/`display_name`) against hand-built `GraphNode`/`TraversalHop` fixtures. No DB or Neo4j.
- `tests/integration/test_impact_analysis_engine.py` — the full engine against a real Postgres pull request/repository, a real Neo4j graph (built by actually running Phase 6's indexer against the real `spring_boot_git_repo` fixture), and a stub `IVersionControlProvider` (the engine doesn't care where changed files come from, so no network call is needed to exercise it end to end) — covers every risk tier, the same-repository Kafka downstream case, persistence/replace-on-rerun, and the not-yet-indexed / not-found error paths.
- `tests/integration/test_pull_requests_api.py` — both endpoints through real HTTP requests, real auth, real ownership checks, with `GitHubVersionControlProvider.list_changed_files` patched at the class level (the same technique `test_github_oauth.py` already uses for the OAuth provider) so no real GitHub account or network call is needed.
- The cross-repository Kafka topic-name matching was additionally verified by hand against two independently indexed copies of the same fixture repository in a real Neo4j instance before being folded into the engine, confirming peers in a *different* repository are correctly found by topic name and excluded from same-repository results.

## Consequences
- Impact analysis is only as good as file-path granularity — a large, multi-concern PR touching one Controller file will mark the whole controller (and everything downstream of it) impacted, even if only one unrelated method changed.
- "Downstream services" across repositories is limited to what Kafka topic-name matching can find; REST-based service-to-service impact only surfaces within a single indexed repository's own graph.
- Re-running analysis after re-indexing (e.g. once the PR merges and `head_ref` becomes the new indexed state) will naturally look different — there is no analysis history to compare against, matching the "always replace" philosophy used throughout this project.
